# Architecture: zed

> Generated by `/map` on 2026-05-20. Covers commit `ad042e5c9d`.

## Overview

Zed is a GPU-accelerated, collaborative code editor built entirely in Rust. It solves the problem of slow, high-latency editor experiences by combining a custom immediate-mode UI framework (GPUI), a CRDT-based collaborative text engine, and deep AI integration into a single native application. The tech stack is pure Rust with platform-specific rendering backends (Metal, Direct3D, Vulkan/Skia) and a server component that uses PostgreSQL and WebSockets for real-time collaboration.

## Directory Roles & Conventions

### `/crates`
**Role:** The entire application lives here as 160+ fine-grained Rust crates. Each crate owns one coherent concern.
**Convention:** No `mod.rs` files are permitted anywhere. Every crate must set `[lib] path = "src/{crate_name}.rs"` in its `Cargo.toml`. Crate names follow explicit suffix conventions: `_ui` for UI components, `_client` for HTTP/API clients, `_server` for server binaries/libs, `_macros` for procedural macros, `_settings` for settings structs, `_types` for shared type definitions. All crates inherit `edition.workspace = true` from the root workspace.

### `/crates/zed`
**Role:** Main application binary and entry point; assembles all other crates into the runnable editor.
**Convention:** This is the only default workspace member. Startup logic lives in `src/main.rs`. No business logic belongs here — it delegates immediately to feature crates.

### `/crates/gpui`
**Role:** Custom GPU-accelerated, immediate-mode UI framework that the entire editor is built on.
**Convention:** Platform implementations are isolated to `gpui_macos`, `gpui_windows`, `gpui_linux`, `gpui_web`, and `gpui_wgpu`. Core logic in `gpui` must not contain platform-specific code. Utility types live in `gpui_util` and `gpui_shared_string`.

### `/crates/text`
**Role:** Low-level CRDT text buffer; the authoritative representation of file contents with conflict-free merge semantics.
**Convention:** Uses Lamport clocks to generate unique operation IDs per replica. Never depends on higher-level editor concepts. Snapshot-based reads (`Buffer::snapshot()`) must remain lock-free.

### `/crates/editor`
**Role:** Primary text editing UI component; owns cursor/selection state, display transformations, input handling, and LSP-driven decorations.
**Convention:** Contains `display_map` as an integrated submodule. The `Editor` struct wraps `MultiBuffer`, not a raw `Buffer`. All position arithmetic works in display space via `DisplayPoint`; translate to buffer positions explicitly when needed.

### `/crates/language_model` and `/crates/language_models`
**Role:** `language_model` defines the abstract `LanguageModel` trait (streaming completions, tool use, token counts, thinking modes). `language_models` is the provider registry that initializes and registers all concrete providers.
**Convention:** Each LLM provider is its own separate crate (e.g., `anthropic`, `open_ai`, `bedrock`). There is no shared HTTP client layer — each provider implements its own. All providers must support `api_url` override for self-hosted deployments.

### `/crates/collab`
**Role:** The collaboration server — both the library and binary. Handles multi-user editing, presence, document sync, and channel management.
**Convention:** This is the only crate that uses PostgreSQL (via sea-orm + sqlx). Server-side session state lives in `crates/collab/src/rpc.rs`. Do not mix client-side and server-side code here.

### `/crates/rpc` and `/crates/proto`
**Role:** `rpc` is the bidirectional WebSocket + Protobuf transport layer shared by client and server. `proto` contains the `.proto` definitions and macro-generated message types (~200+ types).
**Convention:** Protocol version mismatch returns HTTP 426 and must remain a hard error. Message handlers are dispatched by `TypeId`, not string matching.

### `/crates/extension_host`
**Role:** Wasmtime-based sandbox that loads and runs third-party extensions at runtime.
**Convention:** Extensions are compiled to WASM and interact only through the `extension_api` surface (Apache-2.0). No native code execution is permitted for third-party extensions.

### `/crates/settings`
**Role:** Unified settings system with hot-reload, schema generation, and type-safe access.
**Convention:** Use the `RegisterSetting` macro to add new settings; do not hand-write the boilerplate. Settings structs must derive `JsonSchema`.

### `/extensions`
**Role:** Built-in language extensions shipped with the editor (glsl, html, proto, test-extension).
**Convention:** Each extension is an `extension.toml` manifest pointing to WASM artifacts, not a Rust crate. Extensions in this directory are bundled at build time but follow the same WASM sandbox rules as third-party extensions.

### `/assets`
**Role:** Static resources loaded from disk at runtime — fonts, icons, themes, sounds, keymaps, and default settings templates.
**Convention:** Resources are not embedded in the binary; they are resolved from the `assets/` directory relative to the binary at runtime. Do not hardcode asset paths in crate logic; use the asset loading infrastructure.

### `/docs`
**Role:** User-facing documentation in mdBook format.
**Convention:** Architecture and internal developer documents (like this file) also live here. Do not put API reference generated from rustdoc here.

### `/script`
**Role:** Build scripts, release automation, and developer utilities (bash, PowerShell, Python, Julia).
**Convention:** Scripts are not part of the Cargo build graph. Platform-specific scripts use appropriate file extensions (`.sh`, `.ps1`).

### `/tooling`
**Role:** Developer-facing build tooling: compliance checker, xtask runner, performance tooling.
**Convention:** The `xtask` pattern is used for custom build tasks invoked via `cargo xtask <task>`.

### `/ci`
**Role:** CI/CD pipeline definitions (GitHub Actions).

### `/nix`
**Role:** Nix flake definitions for reproducible dev environments and packaging.

## Data Flow

### Application Startup
```
main() [crates/zed/src/main.rs]
  → parse CLI args
  → Application::new(platform backend)
  → init crash handler, logging, file system
  → load AppDatabase (SQLite)
  → spawn background tasks (session, system_id, install_id)
  → settings hot-reload setup
  → initialize_workspace()
  → app.run() → GPUI event loop
```

### File Open
```
User opens file
  → Project::open_buffer(path)
  → Worktree finds/creates directory entry
  → Language registry selects grammar
  → Buffer::new() with CRDT engine
  → MultiBuffer::push_excerpts()
  → Editor::new(MultiBuffer)
  → Pane::add_item(Editor)
  → EditorElement renders via GPUI
```

### Text Edit (Local)
```
Keystroke
  → GPUI input event → Editor::handle_input()
  → MultiBuffer::edit()
  → Buffer::apply_op() with Lamport clock increment
  → EventEmitter broadcasts BufferEvent::Edited
  → Editor invalidates DisplayMap cache
  → GPUI schedules repaint → EditorElement::paint()
```

### Collaborative Edit (Remote)
```
Local edit (see above)
  → Buffer::apply_op() generates operation with unique replica_id + timestamp
  → Project sends op via Client → RPC Peer
  → WebSocket frame → Collab Server (crates/collab)
  → Server broadcasts to other connected peers
  → Remote Client receives → routes via ProtoMessageHandlerSet
  → Buffer::apply_remote_op() — CRDTs merge without conflict
```

### LLM Request
```
User invokes AI feature (agent, completion, inline edit)
  → LanguageModel::stream_completion(request)
  → Provider crate (e.g., anthropic) sends HTTPS request
  → Server-sent events stream back tokens
  → Streamed into agent/editor via async channels
  → GPUI re-renders incrementally
```

### Collab Server Message Dispatch
```
Client WebSocket frame
  → rpc::Conn reads frame → MessageStream deserializes Protobuf
  → Peer routes: response? → matching request channel
                 stream?   → matching stream channel
                 new?      → broadcast to ProtoMessageHandlerSet by TypeId
  → Handler coroutine runs in FuturesUnordered (foreground)
    or detached task (background)
  → Response serialized → outgoing channel → WebSocket write
```

## Gotchas

- **No `mod.rs` files:** The project enforces that no crate may use `mod.rs`. Every crate entry point must be `src/{crate_name}.rs`. This is a hard rule checked by the compliance tool in `tooling/`.

- **Asset loading is runtime, not compiled-in:** Resources in `assets/` are read from disk at runtime relative to the binary, not embedded. Missing assets fail at runtime, not compile time.

- **`sum_tree` is foundational everywhere:** Text ranges, diagnostics, selections, and file trees all depend on `crates/sum_tree`. Understanding its summary-based B-tree is prerequisite to understanding any indexed structure in the codebase.

- **`MultiBuffer` is what `Editor` edits, never a raw `Buffer`:** The editor always operates on a `MultiBuffer` that may interleave excerpts from several files. Single-file editing is just a `MultiBuffer` with one excerpt. This is why diff views and search results can appear as editable inline views.

- **Display positions vs. buffer positions are different coordinate spaces:** `DisplayPoint` (screen row/column after soft-wrapping and folding) is not interchangeable with `Point` (buffer row/column). Always translate explicitly via `DisplayMap`.

- **CRDT merge is replica-scoped:** Each `Buffer` has a `replica_id`. Operations carry `(replica_id, lamport_timestamp)` pairs as their identity. Two replicas can generate the same logical edit concurrently; the CRDT ensures convergence without a lock or server round-trip.

- **Snapshot-based reads are lock-free:** Almost all read operations take an immutable `Snapshot` type. The live `Buffer` or `Worktree` can be mutated concurrently while the snapshot is being read. Do not hold a snapshot longer than necessary — it pins memory.

- **Collab `FuturesUnordered` prevents deadlock, not just ordering:** The foreground message handler pool uses `FuturesUnordered` so that a slow handler on message N does not block message N+1. This explicitly avoids A-waits-B-waits-A deadlocks over the RPC protocol.

- **Protocol version mismatch is a hard error (HTTP 426):** There is no backward-compatibility layer. Client and server must be at the same protocol version. This means the Zed auto-updater is part of the required correctness story.

- **LLM providers each have their own HTTP client and `api_url` setting:** There is no shared HTTP abstraction for AI providers. Every provider crate implements its own HTTP logic, and all support overriding the endpoint URL in settings — enabling self-hosted or proxy deployments without code changes.

- **`collab` is both a library and a server binary:** `crates/collab` compiles as a library (used in integration tests) and as a binary (the actual server). Server-only infrastructure (PostgreSQL, S3, Kinesis) lives exclusively here and must not leak into client crates.

- **Extension marketplace providers are dynamic:** Third-party extensions loaded via Wasmtime can register new LLM providers at runtime via `ExtensionInstalled` events. The provider registry is not static at compile time.

- **`ZED_SERVER_URL` and `ZED_RPC_URL` env vars override all settings:** These are `LazyLock` statics evaluated once at startup. Setting them (e.g., in a container) fully redirects collaboration and RPC traffic regardless of user settings files.

- **PR release notes are mandatory:** Every pull request must include a "Release Notes:" section with a single bullet using one of: `Added`, `Fixed`, `Improved`, or `N/A`. CI enforces this.
